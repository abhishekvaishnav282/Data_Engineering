What is Azure Networking?

Azure Networking is a collection of Azure services that allows cloud resources to communicate securely with each other, with on-premises systems, and with the internet.

In simple terms, Azure Networking decides:

  • Who can communicate with whom?
  • How does data travel between services?
  • Which resources are publicly accessible?
  • Which resources should remain private?
  • How do we secure network communication?

Think of Azure Networking as the road and security system of your cloud infrastructure.

1. Real-world analogy

Imagine a company campus.

BuildingsAzure resources (Databricks, ADLS, SQL Database)
RoadsNetwork connections
Security gatesFirewalls and network security rules
Private roadsPrivate networking
Public roadsInternet connectivity

Even though all buildings belong to the same company, you control which buildings can communicate with each other.

2. Important Azure Networking components

These are the main concepts you should understand as an Azure Data Engineer.

1Virtual Network (VNet)

A private network in Azure where cloud resources can communicate securely.

Example: Place Azure Databricks and Azure SQL resources within a private network architecture.

2Subnet

Divides a VNet into smaller network sections.

Example: Separate application resources and database resources into different subnets.

3Network Security Group (NSG)

Controls incoming and outgoing network traffic using security rules based on IP addresses, ports and protocols.

Example: Allow HTTPS traffic on port 443 while blocking unwanted connections.

4Private Endpoint

Provides a private IP address in your VNet to access supported Azure services privately through Azure Private Link.

Example: Access ADLS Gen2 without exposing its data endpoint publicly.

5VPN Gateway

Establishes encrypted connections between Azure networks and external networks, such as an organization's on-premises network.

Example: Connect a company's office network to Azure.

6Load Balancer

Distributes incoming network traffic across multiple backend resources.

Example: Distribute application traffic across multiple virtual machines.

3. How does Azure Networking work? A practical example

Suppose your company has three Azure resources: Azure Data Factory, Azure Databricks, and ADLS Gen2.

You want ADF to trigger Databricks, Databricks to process data, and the results to be stored in ADLS.

Here is what happens:

  1. ADF initiates the pipeline.
  2. ADF communicates with the Databricks workspace/API.
  3. Databricks reads raw files from ADLS.
  4. Databricks transforms the data.
  5. Processed data is written back to ADLS.

Important: These services do not automatically need to be inside the same VNet. Azure provides different connectivity options, including public endpoints, managed networking and private endpoints.

4. Public Network vs Private Network

Hub-and-Spoke Networks and Azure IP Addressing

  1. Hub-and-Spoke Network Architecture – how multiple Azure networks are connected.
  2. IP Addressing and Reserved IP Addresses – how Azure assigns IP addresses inside a subnet.

Let's understand both using a practical example.

1. What is the Hub-and-Spoke model?

The Hub-and-Spoke model is a network architecture in which one central network (Hub) connects to multiple independent networks (Spokes).

Think of it like a company's headquarters connected to different departments.

  • Hub: Central network that manages shared connectivity and security.
  • Spokes: Separate networks containing individual applications, databases, and workloads.

Real-world Azure example

Imagine your company has three workloads:

  • Spoke 1 – Application services
  • Spoke 2 – Azure Databricks and Data Engineering
  • Spoke 3 – Azure SQL and databases

Instead of connecting every spoke independently to every other spoke, they connect to a central Hub.

The Hub can contain shared services such as:

  • Azure Firewall
  • VPN Gateway
  • ExpressRoute Gateway
  • Azure Bastion
  • Shared DNS services

The advantage is centralized network management, security and connectivity.

3. Understanding IP addresses in Azure

Now let's correct your IP address example. You mentioned:

  • 10.1.1.0 – Network address
  • 10.1.1.2 – Gateway
  • 10.1.1.3 – Azure reserved

You're partially correct, but the gateway IP is different.

Assume your subnet is 10.1.1.0/24. This gives us 256 total IP addresses, from 10.1.1.0 to 10.1.1.255.

Azure reserves 5 IP addresses in every IPv4 subnet

IP addressStatusPurpose
10.1.1.0Reserved 1Network address
10.1.1.1Reserved 2Default gateway
10.1.1.2Reserved 3Azure DNS mapping
10.1.1.3Reserved 4Reserved for future use
10.1.1.4First usableAvailable for resource assignment
10.1.1.5 – 10.1.1.254Usable rangeAvailable for resource assignment
10.1.1.255Reserved 5Broadcast address

Based on Azure's standard IPv4 subnet reservation rules. The Azure DNS mapping is not necessarily a physical DNS server at that IP.

Correction: The default gateway is 10.1.1.1, not 10.1.1.2.

Reference: Microsoft documentation on Azure Virtual Network and subnet design.

4. How many IP addresses are usable?

For a /24 subnet:

CalculationAddresses
Total addresses256
Azure-reserved addresses5
Usable addresses251

Formula:

Usable IPs = 2(32 − prefix) − 5

For /24:

28 − 5 = 251

5. Important: What is GatewaySubnet?

Don't confuse these two things:

10.1.1.1
Azure's reserved default gateway IP.
GatewaySubnet
A specially named subnet where you deploy an Azure VPN Gateway or ExpressRoute Gateway.

For example:

Hub-VNet: 10.0.0.0/16
│
├── AzureFirewallSubnet
│   └── 10.0.1.0/26
│
├── GatewaySubnet
│   └── 10.0.2.0/26
│
└── AzureBastionSubnet
    └── 10.0.3.0/26

These are illustrative subnet allocations. The gateway resource receives IP configuration from the GatewaySubnet; it does not simply use 10.0.2.2 as a universal gateway address.

What is Azure DevOps?

Azure DevOps is a Microsoft platform that helps software and data engineering teams plan, develop, test, build, and deploy applications and projects.

In simple terms, Azure DevOps helps developers manage the complete software development lifecycle (SDLC), from writing code to deploying it into production.

Think of it this way:

  • Developers write code.
  • Azure DevOps manages the code and its versions.
  • Pipelines automate building and testing.
  • Deployment pipelines deliver the application to the required environment.

Real-world analogy: Imagine a software development company where multiple developers work on the same project. Azure DevOps acts like a central workspace where they manage tasks, share code, review changes, test applications, and release updates.

1. Main components of Azure DevOps

Azure DevOps has five major services.

1Azure Boards

Used to plan and track project work.

  • Create tasks and user stories.
  • Track bugs.
  • Manage sprints.
  • Monitor project progress.

Example: Create a task called "Develop customer ingestion notebook".

2Azure Repos

Used to store and manage source code.

  • Git repositories.
  • Branching and merging.
  • Pull requests.
  • Code reviews.

Example: Store your PySpark notebooks in a Git repository.

3Azure Pipelines

Automates building, testing and deploying code.

  • Continuous Integration (CI).
  • Continuous Delivery (CD).
  • Automated testing.
  • Deployment to environments.

Example: Automatically deploy updated Databricks notebooks when code is merged.

4Azure Test Plans

Used to manage software testing.

  • Create test cases.
  • Execute manual tests.
  • Track test results.
  • Manage bugs.

Example: Test whether a data pipeline produces the expected output.

5Azure Artifacts

Used to store and share software packages.

  • Python packages.
  • npm packages.
  • Maven packages.
  • NuGet packages.

Example: Store and share an internally developed Python library.

2. How do these components work together?

Imagine you are developing a Retail Data Engineering project.

Azure Test Plans and Azure Artifacts support the development process alongside these steps.

3. What is CI/CD?

This is one of the most important concepts in Azure DevOps.

CI = Continuous Integration

Whenever a developer pushes code changes to the repository, an automated process can:

  • Detect the changes.
  • Build the application or project.
  • Run automated tests.
  • Report failures.
CD = Continuous Delivery / Continuous Deployment

After successful integration:

  • Prepare the application for release.
  • Deploy it to development or testing environments.
  • Deploy to production according to configured approvals and policies.

Example:

Developer writes code↓ Push code to Git↓ CI Pipeline↓ Build + Test↓ CD Pipeline↓ Deploy to Production
